# Generic Action Bridge v1

Protocol v22 adds a bounded generic action request and result envelope. Requests carry a registered action ID/schema, random operation ID, world generation, optional entity identity and lifecycle revision, and at most 64 KiB of action payload. Client player IDs are deliberately absent; the host derives the player and family owner from the authenticated, live peer.

`IGenericActionAdapter<TLocal>` explicitly supplies schema, target kinds, payload validation, authorization, and a host handler. The bridge rejects unknown actions, schema mismatches, stale or unsupported targets, malformed payloads, and denied authorization. It deduplicates by authenticated player plus request ID in a bounded 4096-entry replay cache. Reuse of a retained ID with different request content is rejected. Once an entry is evicted, the bridge no longer guarantees deduplication for that ID; clients must not retry a non-idempotent operation after an unknown outcome. The cache is session-local and is not persisted across reconnects. Adapter execution is synchronous on the bridge's registration thread; the game integration scopes it through `HostCommandHub.RunAsPlayer`, restoring `CommanderContext` even if the handler throws.

Generic action requests pass through the existing addon native-action policy before the action endpoint. Adapters must still define their own family, ownership, range, and resource rules. Declaring an `Authorize` callback makes that policy point explicit, but the framework cannot determine whether its game-specific checks are complete.

Handlers remain responsible for gameplay restrictions (including `HostPlayerAuthority` and family rules) and must publish resulting state through the existing Stage 3 generic state service or existing gameplay replication. The bridge does not discover methods, serialize object graphs, or forward arbitrary input. Action results distinguish executed, rejected, and failed outcomes. If a connection drops before an acknowledgement, the client treats the request outcome as unknown and must not automatically retry a non-idempotent action.

The Core tests exercise the production `GenericActionSessionEndpoint`, generic state service, and registry together with an in-memory synthetic Counter/Enabled adapter. They cover two clients, a late joiner, state reordering, duplicate requests, cross-family denial, lifecycle rejection, replay eviction, thread affinity, and failed results. They do not instantiate Unity's `HostSession`/`ClientSession` classes or the signed TCP transport. Runtime Unity validation is separate and has not been performed. There is no built-in family/range/resource policy: each adapter's authorization callback must enforce the relevant game rules. This stage does not implement an actual game Counter entity, automatic mod action discovery, asynchronous handlers, or persisted replay history across reconnects/session restarts.
