# FamilyTimeMultiplayer Native Intervention Audit

**Audit date:** 2026-10-11
**Scope:** Static review of production source in the current working tree. No implementation code was changed for this audit.
**Runtime status:** This document does not claim a fresh Unity runtime test. Categories and necessity judgments below are source-based unless explicitly called out as uncertain.

## Executive summary

FamilyTimeMultiplayer installs its Harmony patches once, during `Plugin.Awake`, using `PatchAll`. Most hooks are inert or pass through outside the multiplayer role that needs them. The largest gameplay interventions are client simulation gates, lifecycle observation/suppression, family ownership filters, authoritative action routing, and the world-edit forwarding/recording boundary. These are directly tied to one shared world and host authority.

No production hook directly calls `Crosshair.ShowInteract`, changes the crosshair GameObject, or sets the `E` indicator's visibility. `ClientCommandBridge` calls the game's private `CommandService.RefreshCrosshairIndicators()` in two places. The native method only marks its indicator cache dirty; the game's own `CommandService` then recomputes the prompt from its current target, hand and command state. The calls serve authoritative worker-count refresh and post-disconnect cleanup. The source does not establish that either call caused the reported lingering `E`.

The clearest native-presentation concerns are the title-menu `Update` suppression and `StartupStage`'s camera/canvas changes. Both are temporary or restricted to startup presentation, not gameplay replication. They are not confirmed gameplay defects, but they are broader than the multiplayer state boundary needs and merit a focused follow-up. No hook was classified D (confirmed unnecessary) solely from static inspection; recommendations distinguish that from optional UI and evidence gaps.

## Scope and evidence limits

- Production inventory covers `src/FamilyTimeMultiplayer` and `src/FamilyTimeMultiplayer.Core`. Core code contains protocol, policy and state logic, and does not directly hook Unity game methods.
- Harmony is initialized from `Plugin.Awake`; there is no second production `PatchAll` or manual `Harmony.Patch` call in the plugin source.
- The source contains 101 Harmony patch declarations in 22 production patch files and five nested diagnostic probe patches. Harmony's `PatchAll(Assembly)` scans types in the assembly; its `AccessTools.GetTypesFromAssembly` uses `Assembly.GetTypes`, so the nested probe types are included. Their callbacks are guarded by an active diagnostic scenario. See [Harmony.PatchAll](https://github.com/pardeike/Harmony/blob/master/Harmony/Public/Harmony.cs) and [AccessTools.GetTypesFromAssembly](https://github.com/pardeike/Harmony/blob/master/Harmony/Tools/AccessTools.cs).
- The separate `tests/FamilyTimeMultiplayer.RuntimeHarness.Plugin` assembly is not part of the production plugin. It disables itself when `-ftmp-harness-scenario` is absent. It can still run tests if someone installs that test plugin and supplies the argument.
- Harmony ordering with other plugins, live Build105 behavior, and the lingering-E reproduction were not verified in this audit. Compatibility risks below are risks, not confirmed conflicts.

## Classification

- **A — Essential Multiplayer Integration:** directly required for shared state, authority, identities, persistence or synchronized actions.
- **B — Necessary Supporting Integration:** restores or adapts native behavior so it remains correct after multiplayer state changes.
- **C — Optional Multiplayer Presentation:** adds multiplayer-specific UI or visual feedback without owning core game state.
- **D — Unnecessary Native Behavior Override:** proven to have no multiplayer requirement.
- **E — Unclear / Needs Evidence:** the source alone does not establish the right ownership boundary or runtime necessity.

Recommendation terms: **KEEP**, **MINIMIZE**, **ISOLATE**, **REMOVE CANDIDATE**, **INVESTIGATE**.

## Test-only code in production assembly

`Diagnostics` is compiled into the production plugin. Several scenario classes declare nested Harmony probes (`WorldStateScenario`, `CommandMarkerScenario`, `CommandAudioScenario`). `PatchAll` discovers them at plugin startup, even when no scenario is requested. Their callbacks are guarded by `Active`/`_active` references and therefore are observers with no normal-game mutation while inactive. Scenario construction is selected by `-ftmp-scenario`; the production controller does not create a scenario when that launch option is absent. Selected scenarios can intentionally change frame/vsync settings, invoke game actions or alter world objects for measurements, so the launch argument is a meaningful opt-in boundary. This is not the same as the separately built RuntimeHarness plugin.

**Risk:** dormant test probes remain installed on native methods in normal gameplay and add small callback/patch-chain overhead. Their current guards prevent scenario actions from being activated by ordinary input, but this depends on the static active fields remaining unset. A future maintenance improvement is to move probes into a test-only assembly or patch/unpatch them only during the selected scenario. No accidental gameplay activation was confirmed by source inspection.

## External-mod compatibility risks (not confirmed defects)

1. **Suppressed originals:** client simulation gates, client command routing, startup generation, family draw filtering and title input suppression can bypass native method bodies. Mods that add work to those methods may not run in those modes; Harmony ordering may change the observed result.
2. **Private API coupling:** title/session fields, HUD internals, tool state, `CommandService` internals, WolfMama manager/handles, day/weather fields, save menu fields, and command controller constructors vary across game builds. A missing/changed field can disable a feature or fail plugin initialization.
3. **Shared input and target selection:** `OnInteract` interception depends on native target resolution happening before forwarding. Mods that replace `HandService` candidate/hover data or `CommandVisuals` hover updates can change which action is sent. FamilyTimeMultiplayer does not patch `Crosshair.ShowInteract` or camera input directly.
4. **Camera and UI ownership:** `StartupStage` changes camera render state and disables all root screen canvases during startup choice. `NativeTitleMenuInputPatch` skips the entire title update loop while its overlay exists. Both may affect third-party menus/HUDs.
5. **Singleton/global ownership:** `WolfMama.ActiveInstance`, the shader's WolfMama index, `Application.runInBackground`, global Unity render state and static registries are shared resources. They require strict restore/cleanup and can collide with other plugins.
6. **Unity/GPU state:** agent compute-buffer writes, renderer icon draw slicing, and water RenderTexture uploads depend on engine/render backend assumptions. No cross-platform runtime verification is claimed here.
7. **Serialization:** save path redirection/filtering is installed globally but preserves Solo as the default native directory. Third-party serializers that bypass `WorldSerializer.GetPath/GetSessionsFolder` will not follow the Multiplayer collection.
8. **Object lifecycle:** native object creation/deletion and family clone binding are intercepted to avoid client duplication. Mods that mutate objects outside these APIs may not replicate; this is a coverage boundary, not proof of a defect in the hooks.

## Ranked recommendations

1. **MINIMIZE — `StartupStage` (medium severity).** It changes native camera state and disables every eligible root canvas for optional startup presentation. Prefer an additive multiplayer page while leaving the native scene/camera/canvases intact. Preserve the startup choice/generation gate if the product still requires it. Test Solo, Host, Join, cancel, failed world creation, scene transition, and a third-party HUD before changing.
2. **MINIMIZE — `NativeTitleMenuInputPatch` (medium severity).** It suppresses the full native title-menu `Update` loop to protect two custom overlay buttons. Investigate a native menu action/event extension or a deliberately non-overlapping additive button path. Preserve direct Host/Join/Solo entry. Test keyboard, mouse, native buttons, and another title-menu plugin; do not simply delete this Prefix without that test.
3. **MINIMIZE — `TutorialPromptPatch` (medium severity).** It replaces the complete private tutorial initialization coroutine to delay one prompt. Seek a supported prompt/lifecycle deferral so native tutorial behavior remains authoritative. Preserve startup prompt ordering and accepted-tutorial resume behavior; test solo, multiplayer startup, tutorial already accepted, and missing prompt UI.
4. **MINIMIZE — `FamilyIconPatch` (medium severity).** It rewrites native draw-batch fields and re-enters a renderer pass. Prefer a supported family-scoped icon visibility mask if one exists. Preserve owned-family icon filtering, renderer state restoration and extra icon draws; test with other render/HUD mods and on each supported graphics backend.
5. **INVESTIGATE — startup generation pause cleanup (medium severity).** Confirm interrupted `WaitForChoiceThenGenerate` disposes `WorldPauseScope`. Add a bounded runtime test for controller destruction/menu cancellation before changing the implementation.
6. **ISOLATE — nested scenario probes (low severity).** Move test probes out of the ordinary plugin assembly or install/uninstall on explicit scenario start/end. Preserve the current opt-in scenario evidence and check that production startup no longer installs test observers.
7. **KEEP — both crosshair refresh calls.** Current evidence supports a small native cache invalidation, not presentation ownership. Revisit only if a controlled trace shows a refresh call is a necessary cause of the lingering indicator.

Other searched native state: `Time.timeScale` is read for health diagnostics; production code does not write it. Multiplayer sets `Application.runInBackground` only for active sessions and restores the originally captured value during normal controller updates. No production Pup Burritos-specific hooks or third-party mod-specific patches were found.

## Hooks that should remain

- Agent, rigid, prop, water, world edit, weather, day/time, animation and save-state replication observers/gates.
- Client simulation and quick-save/load suppression while role is Client.
- Client action routing and host-side authorization, scoped to the active client bridge.
- Family owner filtering, family persistence, and the minimum family-scoped native data adaptation needed for separate families.
- Hold ownership, remote command context, and disconnect cleanup hooks.
- Native cache invalidation after authoritative worker-count changes and after client bridge detach.
- Additive multiplayer page, modal and replicated command presentation, provided they remain scoped and do not overwrite native targets or control state.

## Follow-up scope (recommendations only)

1. Add runtime boundary checks for startup menu closure, aborted world generation, controller destruction, `runInBackground` restoration, and family restore prompt cleanup.
2. Evaluate the title menu input and StartupStage presentation as separate, isolated UI changes; keep native title/menu event loops where feasible.
3. Test `RefreshCrosshairIndicators` with a controlled target-state capture: no session, host, client with changed worker count, target lost, Escape, and disconnect. Capture native hovered target plus `_indicatorsDirty` and `_showInteract`; do not alter or globally hide the indicator.
4. Maintain a supported-game-build compatibility list for private-field and renderer hooks; run a plugin-interaction matrix when a third-party mod patches the same target.
5. Move diagnostic Harmony observers into a test-only assembly or prove their dormant overhead and inactive-state safety.

## Audit conclusion

FamilyTimeMultiplayer is primarily a synchronization/authority layer, but it does have several native integration points beyond transport: family-scoped command/HUD/icon data, startup/menu/tutorial behavior, held-entity state, and native tool execution. The invasive simulation and lifecycle hooks have clear multiplayer ownership reasons. The principal scope risks are optional startup/title/tutorial presentation and private render/UI APIs—not the two crosshair cache-refresh calls. No confirmed unnecessary production behavior or crosshair defect was established by this static audit.
